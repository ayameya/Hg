# 東京23区 地下通路マップ

東京23区を歩くときに、地下を通る体験をよくするための軽量なWeb地図アプリです。土地勘のない人でも、近くの地下への入口がどこにあり、どちらへ何m進めばよいかが分かるようにしています。

- 23区内の地下通路（駅コンコース、地下街、ビル地下の連絡通路、公共地下道・横断地下道）を表示します。座標は OpenStreetMap（OSM）のデータをそのまま使っています。
- 日時を指定すると、その時刻に通れる通路と入口だけを表示します。初期値は現在時刻で、1分ごとに更新します。
- 現在地（GPS、または外部の測位結果）とコンパスの向きから、近くの開いている入口を方角・距離つきで示します。
- 目的地を選ぶと、「入口まで地上 → 地下 → 出口から地上」の順に、できるだけ地下を通る経路を案内します。
- 白地図は点と線で構成し、道路・鉄道・水域・区境と、23区内のすべての建物（約244万棟、外形を簡略化）を描きます。
- 地下への入口がある建物（1,517棟）はスミレ色（#7058A3）で塗ります。
- 公共施設・準公共施設（国・都・区の施設、警察署・交番、消防署、郵便局、図書館・博物館・美術館、学校、病院、福祉施設、公衆トイレ、公園、大使館など）を約3.2万件表示します。
- 外部のタイルサーバー、CDN、Webフォントは使いません。`docs/` を静的に配信すれば動きます。

## 描画

地図は WebGL の自作レンダラー（`web/src/gl/`、`web/src/map/`）で描きます。WebGL2 が使えない環境では WebGL1 で動きます。

- タイルの読み込み（PMTiles v3）、ベクタタイル（MVT）のデコード、ポリゴンの三角形分割（earcut）、線の太さを持たせた頂点生成は、Web Worker（2〜4本）で行います。メインスレッドは完成した頂点バッファを GPU に転送するだけです。
- 線の太さ・破線・アンチエイリアスはシェーダーで処理するため、ズームしてもタイルを作り直しません。
- 建物は、ほぼ長方形のものを最小外接長方形に置き換え、それ以外は1m単位で簡略化しています（平均4.5頂点）。
- 地下通路ネットワークと経路も、同じ仕組みで GPU に載せて描きます。
- 文字とアイコンだけは Canvas 2D で重ねて描きます。文字はOSの日本語フォントを使うため、フォントファイルは配信しません。

ソフトウェアGPU（SwiftShader、ヘッドレス Chromium）での計測値は次のとおりです。実機のGPUではさらに速くなります。

| 場面 | 1フレームの処理時間（中央値） | 描画命令 / 三角形 |
| --- | --- | --- |
| 東京駅周辺 z16 をパン | 2.2〜2.5ms | 74回 / 約6.8万 |
| 高円寺周辺 z15.2（住宅密集地）をパン | 1.4ms | 約17万三角形 |

## 使い方

```sh
cd web
npm install
npm run build
node serve.mjs
```

`http://localhost:8080/` を開きます。地図タイルは HTTP Range リクエストで読み込むため、Range に対応したサーバーで配信してください（`python -m http.server` は非対応）。GitHub Pages で `docs/` を公開すれば、そのまま動きます。

- 左上の「☰」で日時・表示・経路・レイヤー・凡例・測位の設定を開きます。
- 右上の時刻をタップすると日時を変更できます。黄色のときは現在時刻ではなく指定時刻です。
- 「◎」で現在地とコンパスを有効にします。iPhone では向きの利用許可を求められます。
- 通路・入口・施設をタップすると詳細を表示します。「ここへ行く」「ここへ案内」で案内を始めます。

## 外部測位との連携

無線のスペクトル分析（Wi-Fi・BLE・携帯電話網のフィンガープリントなど）で求めた位置は、次のどちらかの方法で渡せます。ブラウザからは無線の生データを取得できないため、測位は別アプリで行い、このページを WebView などに埋め込んで結果を渡す想定です。

```js
UGMap.setPosition({ lat: 35.68735, lon: 139.76322, level: -1, accuracy: 3, heading: 120, source: "wifi" });
```

```js
iframe.contentWindow.postMessage({ type: "ugmap:position", lat: 35.68735, lon: 139.76322, level: -1, accuracy: 3 }, "*");
```

- `level` は階層（地下1階なら `-1`）です。指定すると、その階の通路にだけ位置を補正（マップマッチング）します。
- `accuracy`（m）に応じて、補正する距離の上限を決めます（最大60m）。
- 外部から位置を受け取ってから15秒間は、GPSの位置を無視します。
- `setPosition` は、通路に補正した位置（`lat`、`lon`、`level`、`edge`、`offsetMeters`）を返します。

ほかに次の関数があります。

| 関数 | 内容 |
| --- | --- |
| `UGMap.clearPosition()` | 現在地を消す |
| `UGMap.onPosition(fn)` | 位置が変わるたびに `fn({lon, lat, level, source})` を呼ぶ |
| `UGMap.setDestination({lat, lon, name})` | 目的地を設定して案内を始める |
| `UGMap.snap(lat, lon, level)` | 任意の点を通路に補正した結果を返す |
| `UGMap.exportAnchors()` | 測位用アンカー点のCSVを返す |

設定パネルの「測位用アンカー点をCSVで保存」では、通路の分岐点・出入口・エレベーター・端点の座標と階層を出力します。フィンガープリントを採取する地点の計画や、測位結果の照合に使えます。

## 歩行センサーによる位置推定（PDR）

地下には無線のシグネチャ（Wi-Fi・BLE など）がない場所が多いため、端末の加速度計・ジャイロ・コンパスから歩行を推定し、通路の形に沿って位置を補正します（`web/src/pdr/`）。設定パネルの「歩行センサー（PDR）」で有効にします。

| 処理 | 内容 |
| --- | --- |
| 歩行の検出 | 加速度の大きさから重力分を除き、上下動の山と谷の組で一歩を検出する |
| 歩幅 | 一歩の上下動の振れ幅から推定（Weinberg の式）。身長を設定できる |
| 向き | ジャイロの回転を積分し、コンパスでゆっくり補正する（地下の鉄骨でコンパスが乱れても急には追従しない） |
| 動作の判別 | 歩行周期・上下動の振れ幅・上下と水平の揺れの比・山谷の非対称性から、平地・上り階段・下り階段を判別する。記録したデータで学習できる |
| エレベーター | 歩いていない間の上下方向の加速度を積分し、昇降量を推定する |
| 気圧 | 外部から渡された気圧（hPa）の変化が落ち着いたところで、階の変化を検出する |

推定には、通路ネットワーク上だけを動くパーティクルフィルタ（`web/src/pdr/filter.js`）を使います。

- 候補（粒子）は一歩ごとに通路に沿って進み、進行方向と通路の向きが合う候補ほど重みが大きくなります。分岐では進行方向に近い枝を選びます。
- 候補ごとに「歩幅の倍率」と「向きの偏り」を持たせています。曲がり角や分岐が目印になり、正しい値の候補が残るので、歩幅とコンパスの偏りが歩くうちに自動で較正されます。
- 階段を検出したら階段の近くの候補を、エレベーターや気圧の変化を検出したら別の階の通路に移った候補を優先します。
- 無線やGPSの測位結果、または「ここにいる」の手動指定を受け取ると、その位置で候補を補正します。
- 何歩も続けてどの候補も進行方向と合わない場合は、推定位置の周囲に候補を撒き直します。
- 通路から外れた場所では、向きと歩数だけで位置を進めます。

### 精度の検証（模擬データ）

実際の地下通路（大手町〜東京駅丸の内側、793m、階段を含む）を歩いたと仮定したデータで検証しています（`web/test/filter.test.mjs`）。

| 条件 | 結果 |
| --- | --- |
| 一歩ごとの向き（ばらつき15°、偏り15°）と歩幅（−12%）を与えた場合 | 経路全体の平均誤差 1.4〜1.6m。通路に拘束しないPDRは終点で約160mずれる |
| 加速度・ジャイロ・コンパス（偏り12°、ばらつき10°）の60Hzの生データを合成した場合 | 1,134歩をすべて検出し、終点の誤差 0.4〜0.7m。フィルタが推定した向きの偏りは+11〜13°、歩幅倍率は×0.98〜0.99 |

どちらも模擬データでの結果です。実地では、端末の持ち方（手に持つ・ポケット・カバン）、人混みでの歩き方、通路の描き方（OSMの線が実際の通路の中心からずれている）などで精度が下がると考えられます。

### 実地データの記録と学習

設定パネルの「センサー記録と学習」で、実際に歩いたときのセンサー値を記録できます。

1. 「記録開始」を押し、歩きながら「平地」「上り階段」「下り階段」「エレベーター」「エスカレーター」「停止」のボタンで今の動作を記録します。
2. 「記録停止」のあと「この記録で学習」を押すと、平地・上り階段・下り階段の判別モデルをその端末用に学習します（端末内に保存）。
3. 「書き出し」で記録をJSONとして保存できます。「記録を再生」で、保存した記録を早送りで再生し、推定の動きを確認できます。

学習前の既定モデルは確度が低いため、階段の判定を位置の補正にも歩幅の補正にも使いません。

### 外部センサーとの連携

ブラウザからは気圧計を読めず、iPhone では加速度・向きの利用にユーザーの許可が必要です。ネイティブアプリの WebView に埋め込む場合は、次のAPIでセンサー値や判定結果を渡せます（`postMessage` の場合は `type` に `ugmap:motion`・`ugmap:pressure`・`ugmap:step`・`ugmap:event` を指定）。

```js
UGMap.pushMotion({ t, ax, ay, az, alpha, beta, gamma });
UGMap.pushPressure(1009.8);
UGMap.pushStep({ length: 0.68, heading: 132 });
UGMap.pushEvent({ kind: "floor", dz: -3.5 });
```

- `pushMotion`：重力込みの加速度（m/s²）と角速度（deg/s）
- `pushPressure`：気圧（hPa）
- `pushStep`：端末の歩数計の一歩
- `pushEvent`：階の変化（m）

`UGMap.estimate()` で現在の推定（位置・階・ばらつき・歩幅倍率・向きの偏り）を取得できます。

## 通行時間の決め方

地下通路の区間と入口ごとに、次の優先順で通行時間を決めています。区間や入口をタップすると、根拠と確度を確認できます。

1. `pipeline/overrides/hours.json` の個別ルール
2. 駅探の出口情報（入口のみ。23区内の486駅・1,866出口のうち、利用時間の注記がある301出口）
3. OSM の `opening_hours` タグ
4. 施設種別ごとの推定値（確度: 低）

| 種別 | 推定値 |
| --- | --- |
| 駅構内・駅コンコース | `05:00-01:00` |
| 地下街 | `06:00-24:00` |
| ビル地下・連絡通路 | `07:00-23:00` |
| 公共地下道・横断地下道 | `24/7` |

- 駅探の注記にある「初電」は5:00、「終電」は0:30として近似しています。
- 入口・エレベーター・改札・柵・扉のノードが閉まっている時刻は、そのノードに接する区間を通行不可として扱います。
- 時刻の文字列はビルド時に `opening_hours.js` で「月〜日＋祝日」の週間スケジュールに変換しています。ブラウザ側は、このスケジュールと自前の祝日計算（`web/src/holidays.js`）だけで判定します。
- 祝日計算は、2022〜2035年の全日について `opening_hours.js` と照合しています。差は2026年9月22日と2032年9月21日の「国民の休日」だけで、`opening_hours.js` 側がこの2日を祝日として扱っていません。

### 個別ルールの追加

`pipeline/overrides/hours.json` に追記して、`pipeline/underground.py` と `web/tools/compile-hours.mjs` を再実行します。

- `edges`: 通路区間のルール。`match` で対象を指定します。
  - `polygon`: GeoJSON Polygon の座標配列。範囲内の区間が対象です。
  - `area_names` / `area_regex`: OSM の同名ポリゴンの範囲内が対象です。
  - `ways`: OSM way ID の配列です。
  - `name_regex`: 通路名の正規表現です。
  - `categories`: 種別（`station` / `mall` / `building` / `public`）で絞り込みます。
- `entrances`: 入口のルール。`center` から `radius_m` 以内にあり、出口番号が `refs` に含まれ、`station`（駅名）に一致する入口が対象です。

## データ

| データ | 用途 |
| --- | --- |
| OpenStreetMap（AWS Open Data の planet、2026-09-21版） | 地下通路・入口・道路・鉄道・建物・水域・施設・バス路線・船 |
| 国土数値情報（国土交通省） | 施設の補完：P05 市町村役場等及び公的集会施設（2022）、P28 国・都道府県の機関（2022）、P29 学校（2023）、P14 福祉施設（2023）、P04 医療機関（2020、病院のみ）、P27 文化施設（2013）、P30 郵便局（2013）、P17 消防署（2012）、P18 警察署（2012） |
| 駅探（ekitan.com）の出口ページ | 出口ごとの利用時間。robots.txt に従い、1秒以上の間隔で取得 |

施設は OSM を基本に、国土数値情報のうち OSM に同名の施設が近く（約200m以内）にないものを加えています。国土数値情報の座標は住所から求めたものなので、OSM より位置の精度が低いことがあります。

東京メトロ・JR東日本の公式サイトはデータセンターからのアクセスを拒否しており、東京都交通局のサイトはボット対策のJavaScriptチャレンジがあるため、取得していません。

### 再生成

```sh
python3 -m venv ../venv && ../venv/bin/pip install osmium shapely numpy
sudo apt-get install osmium-tool gdal-bin
# tippecanoe は https://github.com/felt/tippecanoe からビルド
cd web && npm install && cd ..
PY=../venv/bin/python WORK=/path/to/workdir pipeline/build.sh
```

| スクリプト | 内容 |
| --- | --- |

| `pipeline/wards.py` | 23区の境界 |

### 地下通路として抽出する条件

`highway=footway|pedestrian|path|corridor|steps|elevator|…` の way のうち、次のいずれかに当てはまるものです。

- `layer` が負
- `level` がすべて負（`B1` 表記にも対応）
- `location=underground`
- `tunnel=yes`（地下道・横断地下道）

ただし、名前に「親水」「テラス」「遊歩道」などを含む屋外の通路と、`tunnel` も `indoor` もない `highway=path|track` は除きます。

これらにつながる150m未満の階段・エレベーター・エスカレーターを「地上との接続」として加えます。地上の道路・歩道と共有しているノード、入口タグのノード、行き止まりになっている接続階段の上端を「地上接続点」とします。

入口ノードが地下通路につながっていない場合は、60m以内の最寄りの通路ノードへ「仮接続」します。仮接続の通行時間は接続先の通路に準じます。それより遠い入口（753か所）は、位置と利用時間だけを表示し、経路には使いません。

## 既知の制約

- 通路の網羅性はOSMの整備状況に依存します。主要駅や地下街は詳細に描かれていますが、地下通路が描かれていない駅（浅草橋など）や、描かれていないビル地下の連絡通路があります。
- 駅探で利用時間の注記がある301出口のうち、OSMの入口と対応付けられたのは187出口です。残りはOSMに該当する入口がないか、出口番号が付いていません。
- 改札の内と外は区別していません。案内経路が改札内を通ることがあります。
- 地上部分の距離は直線距離の1.25倍で近似しています。
- 歩行センサーによる推定は、模擬データでしか検証していません。実地のデータで判別モデルとパラメータを調整する必要があります。
- 種別ごとの推定値は、施設ごとに異なる夜間の閉鎖時刻を1つの値で近似したものです。
